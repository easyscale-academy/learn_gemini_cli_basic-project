# 理解 Context

> 学习什么是 context、为什么它很重要、以及如何有效管理它，从而从 Gemini CLI 获得更好的结果。

## 为什么要学这个

想象一下：你已经和 Gemini CLI 聊了一个小时。你深入探索了一个话题，问了很多追问，逐步加深了理解。然后你问了一个 30 分钟前讨论过的问题，Gemini 给了你一个模糊或稍有偏差的回答。

发生了什么？你遇到了 **context pressure（上下文压力）**。

你发送的每条消息、Gemini 给出的每个回复、你引用的每个文件——都会在 **context window** 中累积。当这个窗口变得拥挤时，回复质量就会下降。理解这一点是长期有效使用 Gemini CLI 的第一步。

## 什么是 Context？

在日常对话中，"context"（上下文）指的是帮助对方理解你在说什么的背景信息。如果你说"它坏了"，对方需要上下文才能知道"它"指的是什么。

AI 的工作方式也一样。当你和 Gemini CLI 对话时，它在 session 之间没有记忆。它对当前对话的所有了解都存在于 **context** 中——到目前为止的完整对话文本，加上你引用的任何文件或信息。

把它想象成会议室里的白板：
- 一开始是干净的
- 讨论过程中不断写东西
- 写下的所有内容都有助于对话
- 但白板的大小是固定的

## Context Window

Gemini 有一个 **context window**——它一次能处理的最大信息量。

把它想象成电脑的 RAM：
- 大小有限
- 你正在使用的所有东西都占空间
- 满了之后性能就会下降

Gemini 的 context window 非常大——Gemini Flash 和 Pro model 最高可达 **1,000,000 tokens**。这大约是许多其他 AI 工具的 5 倍。但它仍然不是无限的。

### 什么是 Token？

一个 token 大约是：
- 英文中大约 **1 个单词**
- 平均 **3-4 个字符**
- 10 行代码片段大约 **50-100 tokens**

所以 1,000,000 tokens 大约是 **750,000 个英文单词**——大约 10 本完整的小说。这很多！但在实际使用中，加上文件和来回对话，填满的速度比你想象的要快。

## 什么会消耗 Context？

session 中的所有内容都会占用空间：

```
+--------------------------------------+
| System Prompt（技能/命令）             | ~500 tokens
+--------------------------------------+
| 你的第一个问题                         | ~50 tokens
| Gemini 的第一个回答                    | ~200 tokens
+--------------------------------------+
| 你的第二个问题                         | ~60 tokens
| Gemini 的第二个回答                    | ~180 tokens
+--------------------------------------+
| 你让 Gemini 读的文件                   | ~1,000 tokens
+--------------------------------------+
| 你的第三个问题                         | ~70 tokens
| Gemini 的第三个回答                    | ~220 tokens
+--------------------------------------+
| 已使用总量：~2,280 tokens              |
| 剩余：~997,720 tokens (99.8%)         |
+--------------------------------------+
```

看起来很少——确实如此，对于三次交互来说。但真实的 session 会增长得很快：

- 长对话（50+ 次交互）：**10,000-50,000 tokens**
- 读一个大文件：**5,000-20,000 tokens**
- 审查项目中的多个文件：**50,000-200,000+ tokens**

## 长 Context 的问题

### 问题 1：Context Pressure（上下文压力）

即使有 1M tokens，context pressure 也是真实存在的。context 越长：
- 早期的信息可能被"淹没"，变得不那么容易获取
- model 可能会忽略对话早期的关键细节
- 在极长的 context 下，回复质量可能会下降

把它想象成一场很长的会议。即使你有无限的时间，在开了 4 个小时之后，人们开始记不清开头说了什么。AI 也会发生同样的事情——更多的 context 并不总是意味着更好的回复。

**底线：** 更大的 context window 并不意味着不需要良好的 context 管理习惯。它只是让问题出现得更晚。

### 问题 2：Token 浪费

当你开始一个新问题但携带着 50,000 tokens 的旧对话时，Gemini 必须处理所有内容——即使那些不再相关的部分。

这意味着：
- **响应更慢** — 需要处理更多文本
- **成本更高** — 处理 tokens 需要消耗金钱（或 quota）
- **注意力分散** — 重要信息与不相关的历史记录竞争

这就像开会时有人在讨论今天的议程之前，先读一遍之前每次会议的纪要。技术上完整，但很浪费。

## 为什么管理 Session 很重要

这就是为什么 session 管理很重要。使用：
- `gemini` — 新 session = 干净的 context
- `gemini --resume` 或 `gemini -r` — 需要时继续上一个 session
- `/resume` — 浏览并选择过去的 session

**什么时候应该重新开始：**
- 切换到不同的话题
- 开始新的任务
- 当回复看起来混乱或重复时

**什么时候应该恢复：**
- 继续之前完全相同的任务
- 需要 AI 记住你之前在做什么
- 跨越休息的多步骤项目

## 解决方案：文档化策略

这是区分新手和高效 AI 用户的关键洞察：

> **Context 不是记忆。文档才是。**

与其依赖冗长的对话历史，不如把重要信息提取到文档中。然后开始一个新 session，引用这些文档。

### 怎么做

**第 1 步：** 进行一次有效的对话
```
你：有哪些好吃的低卡食物？
Gemini：[详细推荐]

你：哪些最容易准备？
Gemini：[准备技巧]

你：我想选这五种。我应该怎么安排每周的备餐？
Gemini：[备餐计划]
```

**第 2 步：** 结束前，提取成文档
```
你：基于我们关于营养的讨论，我认为关键要点是：
- 好吃的低卡选项
- 简单的准备方法
- 我选择要尝试的食物

请创建一个简洁的 markdown 文档（300-500 字），总结关键推荐和我决定尝试的食物。
格式化好，让我可以保存为 docs/nutrition-plan.md。

Gemini：[生成简洁的总结 markdown]
```

**第 3 步：** 在下一个 session 中，引用该文档
```
@docs/nutrition-plan.md
我想调整我的备餐计划。根据我的方案，你有什么建议？
```

（注意：在 Gemini CLI 中你可以使用 `@` 直接引用文件）

现在你有了一个干净的 context，只包含相关信息——没有 50,000 tokens 的旧对话，只有一个聚焦的 500 token 文档。

## 手动 Context 压缩的工作原理

把文档化想象成 **压缩**。你把一段冗长、漫无目的的对话压缩成一个聚焦的总结。

| 之前（原始对话） | 之后（文档） |
|---|---|
| 50,000 tokens | 500 tokens |
| 包含错误的开始、跑题 | 只有最终决定 |
| 话题混杂 | 聚焦于一个话题 |
| 以后很难引用 | 随时可以引用 |

这正是专业人士做的事情：
- 会议纪要将 1 小时的会议总结为 1 页文档
- 架构决策记录记录决策，而不记录完整的讨论过程
- Changelog 将数十个 commit 总结为可读的摘要

你正在将同样的原则应用到 AI 对话中。

## 什么时候需要长 Context

有时你确实需要长 context——这正是 Gemini 的 1M token 容量真正发挥作用的时候：

- **探索大型代码库** — 阅读多个文件以理解架构
- **深度研究 session** — 在许多先前的交互基础上构建
- **复杂重构** — 同时在 context 中保持多个文件

在这些情况下，不要与 context 对抗。使用它。Gemini 慷慨的 context window 使这些工作流程在较小窗口无法实现的情况下变得可行。

关键是知道区别：
- **长 context 用于探索** — 让它自然增长
- **文档用于知识** — 压缩并保存以供后用

## 动手练习：创建你的第一个文档

让我们练习文档化策略。

### Part A：进行一次对话（5-8 次交互）

1. 启动 Gemini CLI session：`gemini`
2. 问："有哪些健康的低卡食物，而且真的好吃？"
3. 继续追问：
   - 准备方法
   - 你个人会尝试哪些
   - 如何安排每周计划
4. 至少进行 5-8 次来回交互

### Part B：提取成文档

对话结束后，要求 Gemini：

```
基于我们的讨论，请创建一个简洁的 markdown 文档（300-500 字），总结：
- 推荐的食物
- 准备技巧
- 我的每周计划

格式化为一个干净的 markdown 文件，我可以保存为 docs/my-nutrition-plan.md
```

将生成的内容保存到 `docs/my-nutrition-plan.md`。

### Part C：测试一下

1. 打开一个新的 session：`gemini`
2. 引用你的文档：
   ```
   @docs/my-nutrition-plan.md
   我想对我的营养计划做一些调整。你有什么建议？
   ```
3. 注意 Gemini 如何 **不需要** 完整的对话历史就能理解你的计划

### 你应该观察到的

- 新 session 启动时很干净——快速且聚焦
- Gemini 仅从文档就能理解你的计划
- 你没有丢失任何重要的东西——关键决定都保留了
- 对话感觉比继续一个冗长的旧 session 更有效率

## 快速参考

- **Context** — Gemini 当前正在处理的所有内容
- **Context Window** — 最大容量（Gemini Flash/Pro 最高约 1,000,000 tokens）
- **Context Pressure** — 即使有 1M tokens，长 context 也可能淹没重要信息
- **Session 管理** — 保持对话聚焦；用 `gemini -r` 恢复，`/resume` 浏览
- **文档化** — 从对话中提取关键要点到可复用的文档中
- **手动压缩** — 让 Gemini 浓缩重要信息

## 导师寄语：建立可持续的工作流程

文档化策略一开始可能感觉像额外的工作。既然可以继续聊，为什么要写下来呢？

原因是这样的：**context 不是记忆。文档才是。**

一次对话是临时的。当你开始新的 session 时，它就没了。但文档是持久的。它可以搜索、引用和分享。

那些早早养成这个习惯的学员会获得复利效应：
- 他们的项目自然而然地积累了有用的文档
- 他们可以用相关 context 立即启动新的 AI session
- 他们在工作过程中顺便建立了个人知识库

这不仅是 AI 技能——也是专业技能。我认识的最优秀的工程师都是不懈的记录者。他们写东西不是因为必须，而是因为他们知道知识在被记录下来时会产生复利。

从小处开始。在你下一次有收获的 AI 对话后，花 2 分钟让 AI 把关键要点总结成一个文档。就这样。一个小小的习惯，回报巨大。
